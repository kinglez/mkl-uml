# SOLID evidence for this bounded design

This is an author assessment of concrete changes, replacements, clients and source dependencies. It does not infer SOLID from UML arrows or a successful validator. Independent CDR and the actual test evidence are required to challenge it.

| Principle | Design evidence | Actual probe and limit |
|---|---|---|
| S — responsibility | Cart owns cart validity/total, Coupon owns eligibility, policies own pure discount algorithms, QuoteService coordinates one goal, adapters own representation/trusted snapshot setup. Product/CartLine are immutable values; PriceQuote enforces completed-result invariants. | Compare a discount-algorithm change with catalog-format change: the former adds a configured policy, the latter changes adapter conversion. Neither requires moving storage/transport work into Cart or QuoteService. This is a reasoned change axis, not a one-method-per-class rule. |
| O — protected extension axis | QuoteService invokes DiscountPolicy and PolicyResolver without a kind switch. Factories are registered outside the core; wiring may change. | CappedHalfDiscount exists only in extension_demo.py. Register capped_half and a trusted demo Coupon; the existing QuoteService/Cart arithmetic runs unchanged and produces literal 25500/2000/23500. Core-file hashes are observed before/after this exercise; they support source stability during the demonstrated extension, not a claim that no future requirement can change the core. |
| L — common behavior | Every policy accepts every nonnegative integer CNY subtotal; fixed amounts cap instead of requiring subtotal>=amount. Configuration and Coupon eligibility occur before the pure operation. Output is integer0..subtotal, deterministic and mutation-free; invalid-domain inputs share ValueError. | CP-42/43/44 use the same contract helper and independently literal vectors for NoDiscount, Fixed3000, Percentage1000, Fixed50000 and CappedHalf. These cases test lower domain, cap and floor, plus common invalid inputs. Finite cases do not prove all possible subtotals or constrain a malicious injected implementation; AD-09 fails closed on invalid amounts. |
| I — client capabilities | QuoteService's three Protocols offer exactly lookup_product, lookup_coupon and resolve. Pure policies need only subtotal/currency, not a cart, catalog, clock or order API. InMemoryCatalog can implement two ports, while the client receives each narrow contract. | Read the signatures and actual source imports/calls. snapshot/setup are available to the harness/composition root, not the core port types. Python structural typing is not a runtime security sandbox; type annotations do not prevent arbitrary attribute access, so source inspection remains evidence. |
| D — ownership and imports | Application code owns the catalog/resolver Protocols and consumes the pure DiscountPolicy contract. The concrete in-memory adapter depends on core/service types; the composition root wires them. service.py imports no adapters, filesystem, database, clock implementation or registry concrete class. | Actual import direction: core←policies; core/policy contract←service; core/policies/service←adapters; outer scripts/tests→adapters/core. The runtime call from service to an injected catalog does not reverse the source-contract ownership. Contracts and their small default implementations may share a module; no framework package boundary is claimed. |

## Why no further interfaces or patterns

There is no persistent repository, database unit of work, remote gateway, event bus, order factory, clock provider or one-to-one BCE Controller layer. Read-only in-memory quoting and explicit evaluation time do not require those dependencies. The existing seams are justified by RNF-01/04/05 and make a real extension/replacement possible. If the scope adds authoritative production time, redemption, transactions or external integration, revisit the requirements and architecture rather than force the new risks into this demonstration.

## Extension trace and expected results

The extension algorithm is a disclosed **technical variation probe**, not a newly business-approved Coupon rule. It is absent from default registrations and the 30 baseline CP cases. Its local class/kind and literal expected results are documented in `09-reference-implementation/extension_demo.py`, `evidence/extension.json` and CP-44. Review the small added policy/factory/registration, retained source hashes and reused common contract. Interface arrows, a new class count or a test named “SOLID” would not establish these properties.

No universal SOLID conformance or production readiness certificate is issued. This example supports the declared change/substitution scenarios with actual executable evidence and records the limits.
